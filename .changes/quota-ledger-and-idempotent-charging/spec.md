# Spec: 额度可归因且扣费幂等

## Behavior

### 账本与计数器

- 每一次额度变化都写一行 `usage_events`：`id`、`user_id`、`day`、`idempotency_key`、`state`、`reason`、`release_reason`、`ref_id`、`created_at`、`updated_at`。
- `state` 是封闭枚举：`reserved`（已占用，业务未确认）、`committed`（业务已成功且计费）、`released`（已释放，不计费）。
- `reason` 是封闭枚举：`message`（一条用户消息）、`recording`（一段录音的整理）。
- `release_reason` 仅在 `state = 'released'` 时有值，是封闭枚举：`failed`（运行失败）、`stale`（清扫回收）。
- `ref_id` 指向本次消耗的实体：消息的 `messages.id` 或录音的 `recordings.id`。
- `idempotency_key` 在同一用户内唯一：`UNIQUE(user_id, idempotency_key)`。
- "某用户某天用了多少次" = 该用户该日 `state IN ('reserved','committed')` 的行数。`usage_daily.used` 是这个计数的物化，写入与账本行在同一事务内完成，读路径只读它。
- 任何时刻 `usage_daily.used` 必须等于账本派生计数。该等式由测试断言，不允许只靠约定。

### 一次消耗的定义

- 一次消耗 = 一次跑完的 Agent 运行，携带一个此前未出现过的幂等键。
- 只要这次运行正常结束（`finish` 提交），就计入一次；与它产出多少内容无关。
- 运行内部的模型请求次数与工具调用次数不影响计数：一次运行最多产生一次消耗。
- 只有两个入口产生运行：发送一条用户消息，以及一段录音转写成功后触发的整理。
- 直接增删改事项、创建 thread、读取任何资源、登录都不消耗。
- 运行失败时消耗净额为零：先占用，随后释放。`used` 在占用与释放之间会短暂偏高，这是可观测的中间态而非两次扣费。
- 不受限用户（`unlimited`）照常记录每次消耗，只有上限判断被跳过。因此 `used` 可以大于 `limit`，`used` 不表示"还能用多久"。
- 用户看不到结果是常态：关掉客户端后服务端仍会跑完并计费，重试可以免费取回同一份结果。

### 幂等键的两个来源

| 消耗入口 | 幂等键 |
|---|---|
| 文字消息 | 请求体的 `clientMessageId` |
| 录音整理 | `rec:<recordingId>` |

- 幂等键相同即同一次消耗：命中已有账本行时返回首次结果，不新建行、不重跑模型、不重复计数。
- 录音上传不消耗额度，它的幂等键落在 `recordings.upload_key`，`UNIQUE(user_id, upload_key)`。同一键重复上传返回既有 Recording 的当前状态，不新建录音；这条保护的作用是让后续唯一那次整理拿到稳定的 `rec:<recordingId>`。
- 上传请求缺少 `Idempotency-Key` 时退回"每次新建一条录音"的语义，行为与当前一致。

### 两阶段扣费

一次消耗分三段，任一段失败都必须留下终态：

1. **reserve**（短事务）：插入 `usage_events` 的 `reserved` 行，同时 `usage_daily.used` 加 1。账本行插入冲突即命中幂等键，直接返回既有结果。
2. **执行**：跑 Agent 或转写，持续数秒到数分钟，期间不持有事务。
3. **confirm**：业务落库成功时，在同一事务里把账本行置为 `committed`。

失败与中断的处理：

- 业务失败：账本行置为 `released`，`usage_daily.used` 减 1，原因记为 `failed`。
- 进程崩溃：`reserved` 行不会被确认。清扫任务把超过 `QUOTA_RESERVE_TTL_MINUTES`（默认 2）的 `reserved` 置为 `released` 并减计数，启动时跑一次，之后按同一间隔（2 分钟）定时跑。
- confirm 时账本行已不是 `reserved`（清扫先跑完了）：不加计数、不回滚已写入的业务数据，不记告警。事后靠该行的 `release_reason = stale` 识别这种情况。

### 原子判定

- 额度判定与扣减合并为一条条件更新：`UPDATE usage_daily SET used = used + 1 WHERE user_id = ? AND day = ? AND used < ?`，受影响行数为 0 即额度不足。
- 不允许先读 `used` 再在应用层判断后写回。
- 额度不足返回现有 `QUOTA_EXCEEDED`（429）并带 `Retry-After`，账本行与计数在事务内一起回滚。

### 日界

- 账本行的 `day` 按 `QUOTA_TIMEZONE` 计算归属日。
- 消息重试跨天时释放原日的 `reserved`、占用当日额度，用户可能看到两天的数字同时变化，这是产品语义而非错账。
- 录音的计费时刻是转写成功并开始整理时，不是上传时：转写失败的录音不产生任何消耗。
- 录音重试复用 `rec:<recordingId>`，因此永不在新的一天为同一段录音再扣一次。

### 可疑扣费自查

- `GET /api/usage/last-anomaly` 返回当前用户最近一条"没有计费"的账本记录，以及一句可以直接展示的话。
- `state` 是封闭枚举 `none` / `reserved` / `released`：没有可疑记录、仍在占用中、已释放。
- 只取最新一条，按 `created_at` 倒序，同一时刻用 `rowid` 兜底。
- 只读：不写账本、不写消息、不改计数，可以任意重复调用。
- 这是排查与演示入口，不是产品功能；不提供申诉、不改账。

### 演示用的中断开关

- `DEMO_STUCK_PREFIX` 配置后，消息内容以它开头时，本次运行在占用额度、写完用户消息之后直接失败。
- 失败走的是"没有清理"的路径：不退款、不删用户消息、不结账，账本行停在 `reserved`，与进程在运行中途被杀的结果一致。
- 未配置时行为与普通消息完全一致；代码里不含任何固定的触发词。
- 用途是复现"扣了但还没退"且不依赖真的杀进程；生产环境不配置即可关闭。

### 契约

- [`POST /api/recordings`](../../contract/openapi.yaml) 新增可选请求头 `Idempotency-Key`（字符串，8–64 字符）；重复键返回 202 与既有 Recording，状态为该记录的当前状态。
- `Usage`、`SendMessageResponse`、错误码结构都不变。
- 新增 `GET /api/usage/last-anomaly` 与 `ChargeCheck` schema。
- 无新增错误码。

## Alternatives considered

- **按产出计费：只回一句话的运行不计费。** 免掉了"问一句什么时候也收钱"的观感，但计费判据变成"`payload` 里有没有结构化字段"，而那是模型临场决定的：同一句话可能这次收钱、下次不收。一条不能用一句话说完的计费规则，边界永远解释不清。
- **跑完再扣（不做预占）。** 少一个状态机，永远不会多扣。但多端并发时多个请求会同时通过上限判断，模型成本先花掉、账后收不回来；额度就不再是上限。
- **只加日志不加账本。** 日志能回答"扣了几次"，回答不了"哪次扣费对应哪条录音"；对账要靠人肉 grep，且日志不进事务，崩溃时与计数不一致。
- **账本作为唯一事实，去掉 `usage_daily`。** 每次判定都 `count(*)`，改动面覆盖 `UsageDto` 与索引，换来的是少一张物化表；在当前规模下不抵。
- **成功后才扣费（不需要 reserve）。** Agent 执行期间并发请求都能通过检查，超发窗口比现在更大。
- **乐观锁 + 版本号重试。** 与条件更新等价但多一轮重试逻辑，SQLite 下没有收益。
- **Redis token bucket 做额度。** 判定原子且快，但账本仍要落库，等于维护两套真相，还要处理 Redis 与数据库不一致。
- **引入第三方计费（Stripe metered、OpenMeter、Unkey）。** 当前没有支付需求，先用一张表和一条条件更新解决。
- **把幂等键做成全局 Fastify 插件。** 最终形态更整齐，但缓存响应需要接口级语义，先按现有三个消耗点显式传键。

## Areas of concern

- `usage_daily.used` 与 `usage_events` 是同一事实的两种形态。任何绕过 [`quota.ts`](../../server/src/quota.ts) 直接写计数器的代码都会破坏等式，需要一条断言测试守住。
- 幂等键由客户端生成。用户换设备或清数据后，同一次操作会带来新键，服务端无法识别"同一个录音内容"，只能识别"同一次请求"。
- 设备端上传不带 `Idempotency-Key`，仍未防住重复上传导致的重复扣费；固件改动独立成链。
- VIP 由邮箱子串决定，修复前"超过 10 次"的反馈会继续出现，独立成链。
- 清扫与 confirm 竞态下，业务数据已提交但账本已释放，用户得到免费的一次消耗。不回滚是因为回滚要删除已产出的消息和事项，用户体验代价更高；不告警是因为演示阶段日志只留给真实错误，这种情况靠 `make reconcile` 的第三条校验事后发现。计数器与账本永远一致，所以单看账本查不出这类少收。
- Agent 运行超过 2 分钟时，清扫会释放一个仍在跑的任务，这次产出变成免费。TTL 取 2 分钟是为了演示时账目快速收敛，调大即可收紧。
