# Spec: 设备上传即结束

## Behavior

- 状态机：待机（灭）→ 录音中（常亮）→ 上传中（慢闪）→ 拿到 `202` 立即回待机（灭）。不再有轮询阶段。
- 未拿到 `202`（连接失败、非 2xx、响应无法解析）：快闪 10 秒，保留录音，回到待机；按一下重传，长按 2 秒丢弃。
- 串口轨迹：`upload: sending` → `upload: HTTP 202` → `upload: id=...` → `state: idle`，不出现 `poll:` 行。
- 服务端后续转写失败对设备不可见：设备不重试、不报警；失败已退款，App 时间线不出现这场会议，原因看服务端日志。
- `GET /api/device/recordings/{id}` 保留在契约里，设备不再调用。

## Alternatives considered

- **继续轮询**：设备没有屏幕，`failed` 只能靠灯的快闪表达，用户仍要去 App 查；轮询还让 LED 在正常转写期间看起来像卡住。
- **静默后台轮询**：设备侧没有消费者，只多一段状态机和网络请求。
- **上传带幂等键**：要从契约到服务端加一套去重；本次不做，风险记在下面。

## Areas of concern

- 上传的响应在网络层丢失、但服务端其实已经收下时，用户重传会建第二场会议；这是现状就存在的边界，本次没有加重，也没有修掉。
- 转写失败只留在服务端日志；App 没有录音列表，用户只能从「时间线没有会议」推断。需要的话另开变更补 App 侧反馈。
